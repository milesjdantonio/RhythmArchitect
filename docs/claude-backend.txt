RYTHM ARCHITECT: THE AI CHARTER (CLAUDE API) ON THE BACKEND
=============================================================

What this is
------------
When a player generates a beatmap, the browser plays the song's YouTube video once and measures it
(the beat grid and every sound in it, timed to a few milliseconds). The audio never leaves the
browser. The browser sends those measurements to the backend, and the backend asks Claude to chart
the song: which of the measured sounds become tiles on Easy, Medium and Hard, in which of the
4 lanes, which are held. The browser checks the answer and builds the charts.

Claude never sees or hears audio (the Claude API takes text, images and documents, not sound), and
it never places a tile in time: it can only pick sounds by id, so every tile stays on a real sound
at its measured time. Claude's job is the judgment a human charter brings: what to follow (the
vocal in a verse, the drums in a drop), how dense each difficulty is, lane patterns that feel
good and repeat when the music repeats, and where holds and chords go.

The frontend is ready. Until the backend has this endpoint, the frontend uses its own fixed-rule
charts (and the dev mock answers with those rules).


1. What the backend must provide
--------------------------------
One endpoint:

    POST /api/chart        body: ChartRequest (JSON)      200: ChartPlan (JSON)

- Base URL: the same server as the rest of the API (VITE_API_BASE_URL on the frontend).
- Errors: any non-2xx is fine: { "error": "message" }. The frontend then uses its own charts, so
  an error never stops a song being made. Answer 501 if charting is turned off.
- Time limit: the frontend waits up to 180 s (CHART_TIMEOUT_MS in frontend/src/mapping/generate.ts), then uses
  its own charts. Aim for under 90 s.
- Size: a request is about 100-400 KB (5-10 sounds per second of music). Accept up to 4 MB.
- The Anthropic API key lives only on the server (env ANTHROPIC_API_KEY). Never send it to the
  browser.

Types: frontend/src/api/types.ts (ChartRequest, SoundEvent, ChartPlan, PlanNote). Contract summary:
docs/api.md, "The AI charter". Real requests to build and test against: docs/samples/*.json
(regenerate with: node frontend/tools/map-audio.mjs --request).


2. The request (ChartRequest)
-----------------------------
    version     1
    song        { title, artist, videoId?, seconds }        title/artist are typed by the player
    timing      { bpm, offset, meter, lengthBeats, confidence }
                offset = seconds into the video where beat 0 lands; meter = beats per bar
    barEnergy   loudness of every bar, 0..1 (bar k starts at beat k * meter)
    sections    rough 8-bar sections labelled by loudness (Intro/Verse/Chorus/Break/Outro)
    cues        loudness moments: build, drop, break, flash (beats)
    events      every sound found, in time order:
                  id        integer, the only way to refer to a sound
                  t         beat it sounds on (exact; snapped to a 16th when within 20 ms of one)
                  sec       seconds into the video
                  band      low (< ~180 Hz: kick, bass) | mid | high (> ~2.5 kHz: hats, cymbals)
                  pitched   true for a note with a clear pitch (voice, lead, bass); false for noise
                  midi/note its pitch when pitched (60 / "C4"), else null
                  bright    brightness as a MIDI-like number: separates hats (high) from kicks
                  strength  0..1, how much it stands out from the music around it
                  len       how long it rings, in beats (a hold can't be longer)
                  onBeat    on a beat rather than between beats
                  accent    one of the biggest hits of the song, on a bar's downbeat
    rules       { lanes: 4, difficulties: [easy, medium, hard], maxNotesPerSound: 2,
                  minHoldBeats: 1 }   read these rather than hard-coding them

The measurements are good at timing and rough at describing: band and pitched are a guess at
what kind of sound it is, and a dense mix can hide a quiet note under a loud drum. Sections and
cues are a loudness guess; Claude should relabel them.


3. The answer (ChartPlan)
-------------------------
    {
      "mapper":  "Claude charter v1 (claude-opus-5-5)",      shown in the dev tools
      "charts": {
        "easy":   [ { "id": 12, "lane": 1 }, { "id": 40, "lane": 2, "hold": true }, ... ],
        "medium": [ ... ],
        "hard":   [ { "id": 3, "lane": 0 }, { "id": 3, "lane": 3 }, ... ]     same id twice = chord
      },
      "sections": [ { "label": "Verse", "beat": 32 }, ... ],    optional, replaces the measured ones
      "cues":     [ { "beat": 96, "kind": "drop", "strength": 1 }, ... ]   optional, same
      "summary":  "Easy follows the vocal; Hard adds the drums in the chorus."   optional
    }

PlanNote: { id, lane 0-3 (keys D F J K, left to right), hold?, len? (hold length in beats,
defaults to how long the sound rings) }.

What the browser enforces on every plan (frontend/src/mapping/charter.ts, chartsFromPlan). Worth checking
the same on the server and retrying or repairing before answering:
- a note with an unknown id or a lane outside 0-3 is dropped;
- at most 2 notes per sound (a two-lane chord);
- a hold on a sound that rings less than minHoldBeats becomes a tap; a hold never outlasts its
  sound's ring (max 8 beats);
- a hold that runs into the next tile in its lane is cut to end 1/4 beat before it (or made a tap);
- if a difficulty ends up with fewer than 8 tiles (or is missing), the whole plan is rejected and
  the browser uses its own charts.
Section labels drive the visuals: use Intro, Verse, Pre-Chorus, Chorus, Drop, Break, Bridge, Outro.


4. Calling Claude
-----------------
SDK: the official Anthropic SDK for the backend's language (Python: anthropic, TypeScript/Node:
@anthropic-ai/sdk, also Java, Go, Ruby, C#, PHP). Endpoint: POST /v1/messages.

Model: claude-opus-5-5 (Claude Opus 5.5, $4 / $20 per million input / output tokens, 1M context,
128K max output). Use the exact ID string. Notes for this model:
- Thinking is always on and adaptive: leave out the `thinking` parameter (sending
  {"type": "disabled"} or a budget_tokens value is an error). Control depth with
  output_config.effort: "low" | "medium" (the default on this model) | "high" | "xhigh" | "max".
  Start at "high" for charting and measure; drop to "medium" if quality holds.
- No assistant prefill, and no forced tool_choice ("any"/"tool"): to get JSON back, use
  structured outputs: output_config.format = { "type": "json_schema", "schema": ... }
  (the SDKs' messages.parse() helpers validate it for you).
- Stream long answers (the SDK's stream + finalMessage / get_final_message helper), so requests
  with a large max_tokens don't hit HTTP timeouts. Give max_tokens room (e.g. 32000-64000).
- Safety classifiers can occasionally decline a request (stop_reason "refusal"; unlikely for this
  content, but handle it). Opt into server-side fallback: beta header
  "server-side-fallback-2026-07-01" and "fallbacks": "default" in the request; a refused request
  is then re-run on a fallback model in the same call. Always check stop_reason before reading
  the content.
- Handle errors by type: 429 and 5xx are retryable (the SDK retries twice by default); 400 is a
  bug in the request. On any failure, answer the frontend with an error (it falls back).

Sending the sounds: compact them to one line per sound, not the request's JSON (about a quarter
of the tokens):

    id,beat,band,pitch,bright,strength,len,onBeat,accent
    10,11,mid,G#2,89,0.69,0.25,1,0
    11,11.5,high,-,104,0.31,0.25,0,0

plus the timing, the bar energies (one line), and the rules. Put the song title and artist in the
user message as data (they're typed by players); the charting brief goes in the system prompt.

Recommended shape (quality and speed):
  A. One call, small answer: the song plan. Claude reads all the sounds and returns, per section:
     a label, which sections repeat which (so repeats get the same patterns), and for each
     difficulty what to follow there (e.g. "pitched mid sounds, the vocal line"; "low + mid
     unpitched: kick and snare"), a density target and a lane scheme. Plus cues (drops).
  B. Three calls in parallel, one per difficulty: the same system prompt + sounds + the plan from
     A, each returning that difficulty's notes. Mark the shared prefix (system prompt + sounds) with
     cache_control so calls 2-3 read it from cache (cache reads are $0.20 per million tokens on
     this model; the prefix must be byte-identical across the calls).
  C. Server code: validate (section 3), merge into one ChartPlan, answer.
A single call that returns all three charts also works, but its answer is long (thousands of
notes), which makes it slow; split it if it runs near the time limit.

What the Spring Boot backend does (src/java/main/SongMapper.java): one call per difficulty was
still too slow for a full song (a 3-4 minute song ran past the app's 3-minute wait), so each
difficulty is split into stretches of the song on bar lines (about 40 s of music for Hard, 80 s
for Easy and Medium) and every stretch is charted at once, in parallel. Each call still sees the
whole song (the same cached prefix) and is asked only for the notes in its stretch; the server
drops notes outside it. Notes come back as one compact line ("12:1 15:2h 15:3": id:lane, h for a
hold) instead of JSON objects. Easy and Medium run at effort medium, Hard at high. Hard's calls
also return the sections and cues of their stretch. The whole plan has a 165 s deadline; on
failure every open stream is closed so nothing more is spent. With Accept: application/x-ndjson
the answer streams progress lines as stretches finish (docs/api.md), which the app shows.

Output schema for a difficulty call (structured outputs), for example:
    { "type": "object", "additionalProperties": false, "required": ["notes"],
      "properties": { "notes": { "type": "array", "items": {
          "type": "object", "additionalProperties": false, "required": ["id", "lane"],
          "properties": { "id": {"type": "integer"}, "lane": {"type": "integer"},
                          "hold": {"type": "boolean"} } } } } }
If cost or speed matters more, ask for a compact string instead ("12:1 15:2h 15:3 ...") and parse
it on the server; the browser validates either way.

Cost (estimate; measure with the count_tokens endpoint on the samples): a 3.5-minute song has
roughly 1,300 sounds, about 20-25K input tokens compacted. The answer is about 1,500 notes across
the three charts (roughly 10 tokens each as JSON objects), plus thinking. On Claude Opus 5.5 that
is in the region of $0.30-0.70 per song, less with the compact output and caching. A cheaper
model (e.g. claude-sonnet-5-5 at $2 / $10) is an option to test against the same samples if cost
matters; that's a product decision.

Charting happens once per song: the song (with its charts) is saved by POST /api/songs and served
from then on. Cache plans by videoId (and a hash of the request) so a retry doesn't pay twice.
Rate-limit the endpoint per player; it spends money.


5. The charting brief (a starting system prompt)
------------------------------------------------
Tune this against the samples. Keep it stable byte-for-byte between calls so it caches.

  You chart songs for a 4-lane rhythm game (keys D F J K; lanes 0-3, left to right; lanes 0-1
  are the left hand, 2-3 the right). You get every sound measured in the song, each with an id,
  its beat, what kind of sound it is, its pitch, how strongly it stands out, how long it rings.
  Each tile must be one of these sounds, by id: you can't add a sound or move one in time.
  Players hear the song, not their key presses, so a tile on nothing (or a missed obvious hit)
  is felt at once.

  What to follow: what a listener would tap along to. In verses that's usually the vocal or lead
  melody (pitched mid sounds); in choruses and drops, the drums and big hits join in; in breaks,
  the most prominent remaining part. Stay with one idea within a phrase; change at section
  boundaries. Repeated sections get the same patterns.

  Difficulty is density, holds and chords:
  - Easy: the clearest beats and melody notes only, at least 1 beat apart (2 beats above
    150 BPM); holds only on sounds ringing 2+ beats; nothing else while a hold is down; no chords.
  - Medium: more of the melody and the main drum hits, at least 1/2 beat apart (1 beat above
    150 BPM); holds from 1.5 beats; a chord only on the biggest accents.
  - Hard: everything that drives the song, down to 1/4-beat runs where the music has them;
    taps in other lanes during holds; two-lane chords on accents.
  Quiet passages get fewer tiles, not none.

  Lanes: melodies move with pitch (higher notes further right); the same drum gets the same lane
  within a section; alternate hands in fast runs; avoid more than 2-3 fast taps on one lane in a
  row, and awkward jumps between the outer lanes. Holds go only on sounds that really ring (len).

  Answer only in the requested JSON.


6. Testing
----------
- Frontend dev with the mock: npm run dev. The mock answers /api/chart by fixed rules.
  MOCK_CHARTER=off makes it answer 501, to see the fallback.
- Against the real backend: set VITE_API_BASE_URL to it. The dev tools (backtick key, in a game)
  show the "Mapper" line (says "on-device" if the backend's plan wasn't used, and why) and the
  "Charter" summary.
- Unit-test the backend on docs/samples/*.json; the referee for a valid plan is chartsFromPlan in
  frontend/src/mapping/charter.ts (frontend/tests/unit/charter.test.ts shows what it fixes and what it rejects).
- Play the result: the charts should feel like the song. Check that easy is calm, that holds sit
  on sustained notes, and that repeated choruses chart the same.
